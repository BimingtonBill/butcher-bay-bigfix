# v0.4: HUD, subtitles and FOV — EU 1.1 AMD64 static investigation

2026-10-29. No game launch, injected code, DLL loading, binary edits or game
configuration writes were performed. The original investigation covers design
§3 items 15–16 / §3a. The [implementation addendum](#v04-implementation-2026-10-30)
records the subsequent v0.4 changes and remaining runtime acceptance.

## Plain-language result

**The HUD really is drawn on a 640×480 canvas.** The client explicitly scales
its X coordinates by viewport width / 640 and Y by height / 480. At 16:9 these
scales differ, stretching circles, glyphs and icons horizontally. This is
independent of the movie aspect-fit helper: correcting the display's aspect
field alone will not fix ordinary HUD geometry. Confidence: **high**.

**Subtitles and full-screen effects can be separated by their callers.** The
subtitle list has identifying RTTI, and its renderer submits text through
`CRC_Util2D` slot +0x1A8. Fade/background rectangles use +0xF8; ordinary HUD
rectangles use that slot too. Therefore a global rectangle, viewport, or GL
matrix change is unsafe. The engine has useful object/message/render scopes,
but I found no universal flag meaning “this element should preserve 4:3”.
Confidence: **high** for those boundaries; **medium** for complete element coverage.

**The camera matrix builder already supports Hor+ geometry.** With its default
reference aspect 4/3, FOV 90 and square pixels, it produces approximately
106.2602° horizontal / 73.7398° vertical at 16:9. That is Hor+, not Vert-.
The normal player camera request starts at 90°, with dialogue, special-camera
and time-varying modifiers. Confidence: **high** for the formula and defaults,
**medium** that those exact inputs survive unchanged in opening gameplay.

**A separate hands-only FOV setter is not established.** The client saves a
camera viewport that player-model code reads back, including its projection
matrix. Thus the player models are coupled to camera projection; intercepting
all FOV setters would not satisfy “world FOV without breaking the viewmodel”.
There is a promising boundary after the original camera query has saved that
viewport, but preserving the snapshot is not proof that the hands' actual
rasterization projection stays unchanged. Confidence: **high** for the coupling,
**low/unresolved** for an independent hands pass. The trace below is the next
required proof; do not describe a world-only FOV fix as finished yet.

Recommended first implementation: a **centred 4:3 content transform scoped to
verified HUD/text callers**, leaving the world visible at the sides. Keep fades,
screen effects and bars full width. Use `FOV=0` for original camera behavior;
define nonzero values as horizontal degrees at 4:3 equivalent. Preserve authored
cutscene cameras and zoom semantics. Do not change global display aspect fields.

## 1. GUI mapping, aspect sources and element separation

### 1.1 Explicit 640×480 scaling and the CRC_Util2D transform

`GameWorld!0xB890` is the client overlay dispatch (primary `CWClient_Mod` vtable
`0x1DEF08`, slot +0xA50). It initializes the embedded util at client +0x4F8
from the current renderer viewport, then sets its two independent scales:

```asm
; GameWorld_Win64_AMD64.dll
0000b985 call qword ptr [rax + 0x80] ; current CRC_Viewport
0000b990 mov ecx, dword ptr [rax + 0x44]
0000b995 mov ecx, dword ptr [rax + 0x48]
0000b99b mov ecx, dword ptr [rax + 0x4c]
0000b9a1 mov eax, dword ptr [rax + 0x50]
0000b9c8 divss xmm0, dword ptr [rip + 0x1d25f0] ; constant 640
0000b9db divss xmm1, dword ptr [rip + 0x1d25d9] ; constant 480
0000b9fe call qword ptr [rax + 0x60] ; util scale setter

0000ba8b mov edx, 0x81
```

The two literals are floats at `GameWorld+0x1DDFC0` (640) and +0x1DDFBC
(480). The same explicit division appears in menu render `0xEECB0`, calls
`0xEEDA4`, `0xEEDB7`, `0xEEDD2`. Installed `CubeWnd.xrg` defines its roots as
`*RGN 0, 0, 640, 480`, including `demo_main`, `demo_mainreal`, and video roots.
This is corroborating layout data, not proof that every shipped menu uses a
particular root name.

|---|---|---|

This uses a fixed-depth 2D transform combined with the viewport projection;
calling it literally `glOrtho(0,640,480,0,...)` would be inaccurate. RndrGL
uploads a matrix. Aspect preservation is defeated by the explicit independent
W/640, H/480 mapping: at 2560×1440 one logical X unit spans 4 physical pixels,
one Y unit spans 3. A global viewport fix would also affect world rendering,
clipping, screen effects and other engine views.

### 1.2 Three distinct “aspect” quantities

Do not conflate UI layout `PIXELASPECT`, display aspect and viewport pixel ratio.

* **Display screen aspect**: context +0x44, normalized to 4:3; getter slot
  +0x80. `RndrGL+0x47ED0` reads it. `MSystem!SetScreenRatio` at `0x146930`
  computes `0.75 * width / height * suppliedPixelAspect`, then calls setter +0x78.
* **Display pixel aspect**: context +0x48, getter +0x90 / setter +0x88;
  `RndrGL+0x47EF0` / +0x47EE0. The options-to-engine bridge copies
  `VIDEO_DISPLAY_PIXELASPECT` to the environment/console variable
  **`vid_pixelaspect`** (literal lowercase; do not assume an independent
  `VID_PIXELASPECT` startup-config reader has been proven).

  definitions and passed as the fifth argument to `0x39AD0`. It describes
  that UI image's intended shape; it is not a global HUD correction switch.

| Content | Proposed v0.4 treatment | Static discriminator / limit |
|---|---|---|
| Subtitle glyphs and shadow | Centred 4:3 region, same line wrapping and logical margins | `GameClasses+61AF0`, +1A8 calls; high |
| HUD icons, health/ammo, crosshair | Preserve shape in centred 4:3 region | Player +21C500 proven for its content; remaining callers require trace |

For 2560×1440, safe content width is 1920, left margin 320. Logical mapping is
`x' = 80 + 0.75*x`, `y'=y` on the 640×480 canvas; physical world rendering
continues across all 2560 pixels. **Do not clear black HUD sidebars.**

Safest initial hook proposal: scope `GameClasses!0x61AF0` and the verified
content in `0x21C500`, then apply a post-transform to util geometry/text only
while that scope is active. Deduplicate nested scopes (mod overlay calls base
subtitle, which then sends player message 81h). Util scale setters can rebuild
the matrix; intercept/reapply after those setters within scope, restoring at
exit. Its transform begins at util +0xBC; a centred horizontal contraction in
view coordinates must affect the entire X-output column, not just one diagonal.
Clipping/scissor, glyph size, shadow offsets and cached/deferred submissions
must receive the same mapping. A semantic scope plus receiver check is safer
than classifying by rectangle size/texture=0. Per-element edge anchoring can
come later after all origins are understood; it is higher risk than one
consistent safe region and risks splitting compound icons/text.

## 2. Projection, FOV and first-person coupling

### 2.1 Projection owner and formula

The names below are actual **MSystem exports**, not invented function names:
`CRC_Viewport::SetFOV` +0x4B2C0, `SetFOVAspect` +0x4B2D0,
`SetAspectRatio` +0x4B2F0, `SetPixelAspect(float,float)` +0x4D610,
`Update` +0x56C40 and `GetProjectionMatrix` +0x57650.

| CRC_Viewport offset | Meaning |
|---|---|
| +0x00 | mode 0=FOV, mode 1=explicit scale |
| +0x04 | FOV in degrees, constructor 90 |
| +0x08 | reference FOV aspect, constructor 4/3 |
| +0x0C | explicit/derived scale |
| +0x10 | aspect correction, constructor 1 |
| +0x14/+0x18 | pixel X/Y inputs, constructor 1/1 |
| +0x1C/+0x20 | derived X/Y scales |
| +0x24/+0x28 | near/far planes |
| +0x2C | clip context |
| +0x44..+0x50 | view rectangle |
| +0x54 | dirty flag |
| +0x58 | engine projection matrix (before GL convention conversion) |

```asm

0005290e mov dword ptr [rcx + 8], 0x3faaaaab ; 4/3
00052915 mov dword ptr [rcx + 0xc], 0x3f800000
0005291c mov dword ptr [rcx + 0x10], 0x3f800000

00056ce6 cvtss2sd xmm0, dword ptr [rcx + 4]
00056ceb mulsd xmm0, qword ptr [rip + 0x182d5d] ; pi
00056cf3 divsd xmm0, qword ptr [rip + 0x182d4d] ; 360

```

The comparison at +0x56D54 looks like an aspect-dependent policy, but its two
branches perform the **same arithmetic**, then converge at +0x56DA5. It is
not evidence of a Hor+/Vert- switch. For a centred full viewport, let
`A=W/H`, `B=viewport[8]`, `P=viewport[10h]`, `Px=viewport[14h]`, `Py=viewport[18h]`.
After RndrGL normalization the diagonal magnitudes are:

`abs(m00) = B*cot(F/2)*Px/(A*P)`;
`abs(m11) = B*cot(F/2)*Py`.

The math callee identities are corroborated by their own error paths:
`MSystem+0x19D0A7` references the string `cos` at +0x21393C;
`+0x1A01D7` references `sqrt` at +0x216038, and +0x1A01F6 executes `sqrtsd`.

At defaults `B=4/3`, `P=Px=Py=1`, vertical FOV is constant as A grows. F=90
means H=90,V=73.7398 at 4:3 and H=106.2602,V=73.7398 at 16:9. This is a
derived static prediction; log the live fields before claiming measured Hor+.
`SbzEngine!0x39950` is a viewport-resolution adapter: +0x399E9 gets display
pixel aspect; +0x39B22 sets viewport aspect, +0x39B3C sets pixel X/Y ratio.
It is shared infrastructure, not a world-only FOV option boundary.

```asm
; RndrGL.dll
000095f7 call qword ptr [r11 + 0x80] ; current viewport
00009604 call 0x65aa4 ; MSystem GetProjectionMatrix import thunk
00009658 call qword ptr [rip + 0x8557a] ; glViewport
00009692 call qword ptr [rip + 0x855c0] ; glMatrixMode(GL_PROJECTION)
000096c0 divsd xmm0, xmm1 ; 2 / width
000096d2 divsd xmm2, xmm0 ; 2 / height
00009754 call qword ptr [rip + 0x85486] ; glLoadMatrixf
00047767 call qword ptr [rip + 0x4741b] ; glFrustum, separate context/setup path
```

The final camera upload is in `RndrGL!0x95A0`, not in the lone `glFrustum`
call. The latter at +0x47767 has fixed literal bounds and sits in context/render
target initialization (`0x476A0`), not the demonstrated per-viewport matrix
builder. MXR consumes `CRC_Viewport` too (e.g. `Update` calls +0x3C3C0 and
+0x3C3D9); it is not the owner of the basic FOV formula. Hooking only GL would
leave engine culling, projected positions and other matrix consumers inconsistent.

### 2.2 Actual player FOV values and authored cameras

`GameWorld!0x136EF0` copies the current renderer viewport into the output,
sends message **0x24**, first to the controlled object, then the player object
as fallback, and saves the result at client +0x78C. `GameClasses!0x20E080`
handles that message. Its normal FOV starts at **90**. If player flag bit 0x1A
is set, it queries another object with message 0x26 and falls back to the byte
at client-data +0xCF8. Bit 0x17 instead calls the dialogue camera FOV interpolator.
Another state (`+0x10F4 == 2`) chooses **110**. Otherwise interpolated controls
at +0x1320 and +0xCFC modify FOV before `SetFOV`.

```asm
0020e474 addss xmm9, xmm8
0020e48a call 0x264e42 ; MSystem SetFOV
001db8d0 mov byte ptr [rbx + 0xcf8], 0x5a ; restore authored 90
```

`GetDialogueCameraFOV_Client` is identified by its error string at
`GameClasses+0x2CC1D8`. Function +0x1EA450 interpolates camera data at
+0x790/+0x820 using client time; its missing-data fallback is 90. Treat these
as authored cameras. The two time-varying controls above are proven modifiers;
their exact gameplay names (weapon zoom, movement/special effect) are **not**
fully established. Never replace every incoming FOV by a fixed configured value:
that erases these transitions and can disable zoom.

The console/viewport setting `VP_FOV` also exists in `SbzEngine!0x1E350`
(default 95 at +0xAB6E0). It is a generic viewport object setting, not evidence
of a persistent player FOV option: the player's message 0x24 sets FOV again.

### 2.3 Viewmodel: what is proven, what is still missing

The world camera setup `GameWorld!0x136DD0` calls client vtable +0x658
(`0x136EF0`) and then renderer +0x88 to install that viewport.
Client +0x660 (`0x136DB0`) returns the saved +0x78C viewport. Player-model
rendering at `GameClasses!0x219C40` reads this copy and asks for its projection:

```asm
; GameWorld_Win64_AMD64.dll
00136e1e call qword ptr [r11 + 0x658]
00136e34 call qword ptr [rax + 0x88] ; install camera viewport
00136db6 mov r8d, 0x13c
00136dbc lea rdx, [rax + 0x78c]
00136dc3 jmp 0x1aebc0
; GameClasses_Win64_AMD64.dll
0021a7be call qword ptr [r8 + 0x660] ; client saved viewport
0021a7cd call 0x264e54 ; GetProjectionMatrix
0021a7d5 lea rcx, [rbx + 0x74c]
0021a7e4 call 0x1c7c0 ; matrix multiplication, not a FOV setter
```

This identifies a **projection consumer in player-model rendering**, not an
independent “weapon FOV = X” function. Its branch conditions include player/model
state, so claiming every call is the visible hands would overstate static RE.
The other GameClasses `SetFOV` site +0x218BC6 sets a small viewport rectangle
`(10,30)-(510,80)`; that is not evidence of the main full-screen viewmodel pass.
Likewise screen-effect scopes temporarily set 90: they are not automatically
hands projections. No verified independent hands `glFrustum` site was found.

Recommended FOV boundary to **instrument first**: detour
`GameWorld!0x136EF0(client, outputViewport)`, call original, retain its authored
camera result and saved baseline +0x78C, then modify the world output before
`0x136E34`. This lets the engine derive culling and projection from the same
world FOV. Do not modify the globally shared `MSystem::Update` or setters.
However, the saved baseline may be used for screen-space targeting/laser
placement as well as models. Confirm those consumers before deliberately
separating it from the world output. If the visible hands share the active
world projection, the complete fix needs a verified first-person submission
boundary: give only those models their original projection, or compensate their
model-to-clip transform by `inverse(P_world_new) * P_viewmodel_original` in the
engine's actual matrix convention. Do not apply that formula to all player/body
models, shadows, weapon-world models, or the unproven +0x21A7E4 multiply.

Suggested setting contract:

* `FOV=0`: original camera behavior. Nonzero: horizontal degrees at 4:3
  equivalent, matching this engine's FOV units at default B=4/3. Validate finite
  values, with a conservative supported range such as 60–120; never pass NaN or
  the engine's near-singular 179° limit through unchecked.
* For normal first-person view, change world output before culling. Preserve
  original near/far, view rectangle, reference aspect and pixel settings.
* Retain zoom by scaling the tangent of the authored half-angle relative to
  the normal baseline: `tan(Fnew(t)/2) = tan(Fold(t)/2) * tan(Fsetting/2)/tan(90/2)`.
  This is a proposed policy, not recovered game code. It preserves magnification
  ratios; a flat degree replacement or addition does not.
* Leave bit-0x17 dialogue and bit-0x1A external-camera branches authored by
  default. Trace ambiguous special states (including 110°) and skip them until
  categorized. Do not infer a cutscene solely from FOV != 90.
* Preserve or separately compensate the viewmodel only after positively
  identifying its pass. “Snapshot unchanged” alone is insufficient acceptance.

## v0.4 implementation (2026-10-30)

Implemented in `src/widescreen_{hooks,math,sites}.cpp`, with settings in the
existing INI parser and deferred module handlers. The installed game files were
read as PE data only. No game launch, game DLL loading, captures or game writes
were performed by the implementation worker.

### HUD policy and ownership

`HudAspectFix=1` (default) detours the verified `GameClasses+61AF0` subtitle list
and `+21C500` player HUD boundaries. A TLS receiver scope precomposes the util's
complete X/Y coordinate bases and translation at `util+BC`, mapping the logical
640×480 canvas into the largest centred 4:3 rectangle. At 2560×1440 it maps
logical X to `80 + .75*x`, leaving Y unchanged. At 5:4 it contracts Y instead;
invalid dimensions preserve the original matrix. No black HUD sidebars are drawn.

All compound 2D HUD items use this one centred region; no per-texture anchoring
heuristics are used. The ordinary health mesh renderer (`+2187C0`) uses its own
physical 3D viewport, rather than the util's 2D matrix, and keeps its existing
upper-left anchor and projection. Its original requested rectangle is
`(10,30)-(510,80)` with a `(0,0)-(640,480)` clip. That native 3D path is not
stretched through the 2D canvas. Other HUD content is corrected only when it
actually passes through the two verified util scopes; opening-dock coverage of
health, crosshair and contextual indicators must still be checked visually.

The `GameWorld+36BB0` matrix rebuild detour reapplies the mapping after scale,
depth or viewport setters rebuild it. Each scope retains the latest original
matrix and restores it exactly at exit; nested scopes for the same receiver do
not apply it twice. Original scales, logical clipping/wrapping and glyph/shadow
layout are retained, so CPU-clipped geometry is transformed consistently and
queued vertices already carry the corrected positions. The receiver must have
the verified `CRC_Util2D` vtable address. A missing rebuild hook disables scope
mapping. The shared rectangle/text methods, global GL matrix and viewport are
not narrowed. In particular, `+5060`, `+5B10`, `+69010`, the movie background and
menu controls are not added to the allowlist.

### Menu/title compositor investigation and correction

The shipped `main` root is `CubeMenu`, not an ordinary full-canvas image.
`GameWorld+5CA60` calls `CWFrontEnd_Mod` slot `+128` at `+48C90`. Its background
compositor copies the current viewport, sets its own 90° FOV and aspect correction
1, and calls `MSystem::CRC_Viewport::GetViewVertices` via `GameWorld+48F5D`.
It immediately copies the centre and four returned corners onto its stack.
The cube/menu controls then render separately.

There is a statically demonstrable coordinate mismatch for clipped viewports:
`MSystem+573E1` constructs those corners from the **requested** rectangle at
viewport `+44..50`, whereas `+56EAA` constructs the off-axis projection from the
intersection with clip bounds (`+34..40`). RndrGL normalizes that projection
against `GetViewArea` (`MSystem+529D0`), i.e. the **clipped** physical rectangle.
Using requested-frustum corners as the fullscreen background therefore does not
in general cover the same rectangle as the uploaded projection. Integer half
sizes also require care for odd dimensions.

The implementation detours `MSystem+57790` and substitutes corrected corners
**only** for the verified `GameWorld+48F62` return address. After the original
has updated the projection, it solves each corner's X/Y against that matrix and
the clipped view dimensions, retaining depth, winding and the centre vertex.
The returned TLS array is copied synchronously by the original caller. No engine
viewport, cached vertex array, UVs, menu hit testing or cube animation is changed.
This correction follows `HudAspectFix`; invalid/unsupported projection shapes
and mismatched bytes pass through unchanged.

The compositor also has a separate cached-screen branch (`+490DC..49157`) that
rounds texture sizes up to powers of two unless renderer capability bit 21 is
set. Its artwork branch uses `853/1024` U coverage and `853/512` reference aspect
(constants `+1E8328/+1E8324`). These values are internally consistent padding/fit
inputs; they are not changed speculatively. The global 2048 texture cap already
has the existing `TextureSizeFix` owner. **The lead must confirm whether the
projection alignment eliminates the specifically reported right/bottom strips
at 2560×1440.** Static evidence proves the clipped-frustum mismatch, not that the
reported run had that clip state. If the strips persist, the menu defect remains
open; do not describe this candidate as visually confirmed.

### FOV and hands decision

`FOV=0` preserves the original camera. A finite nonzero value in 60–120 is
horizontal degrees at 4:3 equivalent, not the final widescreen horizontal angle.
The camera remains Hor+ using the engine's existing reference aspect.

`GameWorld+136EF0` is called normally first. While it is active, a detour of
`GameClasses+1E33B0` observes only its verified `+20E2AC` camera-query caller.
That gives the actual topmost controlled player object and client-data result
used by the original handler. Bit 23 (dialogue), bit 26 (external camera), mode
2 (the unidentified 110° camera), missing client data and unclassified camera
implementations are excluded. No fixed-FOV replacement of all SetFOV calls is
performed. The normal output follows:

`new = 2*atan(tan(authored/2) * tan(configured/2) / tan(90/2))`.

This retains relative tangent magnification, including the original interpolated
modifiers. All other viewport fields remain original except FOV and its dirty
flag. The adjusted output is also copied into client `+78C`, so culling, screen
projections and saved-viewport consumers agree. This deliberately does not use
the unproven saved-snapshot trick to claim a separate viewmodel projection.

Further static inspection still establishes only that `GameClasses+219C40`
consumes the saved projection at `+21A7BE/+21A7CD`. It does not establish a safe
visible-hands-only submission boundary. Therefore **hands/weapon projection
remains coupled**, world/gameplay FOV is opt-in, and the README explicitly says
that hand size/perspective may change. The roadmap's independent-viewmodel
acceptance is not claimed.

### TraceFov

`TraceFov=1` observes the existing shared `glLoadMatrixf` detour; there is no
second competing GL hook. The renderer's six call bytes at `RndrGL+9754` must
match before the observer accepts return address `+975A`. It records every
upload in order within a sampled frame, including repeated matrices, as all 16
floats plus frame/thread/context IDs and symmetric H/V estimates. Off-axis
matrices must be interpreted using the complete matrix, not those estimates.
Camera records include authored/output FOV, classification and view rectangle.

Sampling: process frames 0/1, first two classified gameplay frames, then every
120th presented frame; at most 48 uploads per sampled frame, 96 payload lines
before gameplay, and 400 total payload lines including the final limit marker.
Frame IDs advance on successful swaps through the existing capture owner.
Setup/failure log lines are separate. No GL state is modified, no strings from
subtitles are read, and no file path or story data is traced. Other trace/fix
settings retain ownership of their existing GL hooks.
